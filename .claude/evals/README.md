# natural-japanese eval suite

`~/.claude/skills/natural-japanese` の**リグレッション検知**と**発火範囲の監視**を目的とする。
uplift（Δ）の大きさを誇るための suite ではない。理由は「測定の限界」を参照。

## 実行

```
claude plugin eval . --ablation with-without --judge-model sonnet --allow-tools Write Edit
```

レポートをローカルに留めるなら `--no-publish` を足す。
1回あたり約 $10.5（7ケース × 3ラン × 2アーム）、所要およそ 25〜30 分。

## ケース構成

| slug | 種別 | 何を見るか |
|---|---|---|
| `01-slide-copy` | 発火 | AIスロップを重ねた冗長なスライド文言の圧縮 |
| `02-memo-from-bullets` | 発火 | ノイズ混じりの箇条書きから、判断依頼が先頭に立つメモを書けるか |
| `03-mail-rewrite` | 発火 | 180字級の一文を含むメールの分解（機械判定: 80字超の一文がゼロ） |
| `04-report-conclusion-first` | 発火 | 結論が末尾に埋もれた報告の再構成 |
| `05-facts-dense` | 発火 | 2社の数値を指示語で入れ違いに参照する原文で、会社と数値の対応が壊れないか |
| `06-neg-minutes` | **非発火** | 文字起こし→議事録化で発火しないこと（実運用では call-summary の担当） |
| `07-neg-md-to-html` | **非発火** | Markdown→自己完結HTMLで発火しないこと |

各ケースは `plugins: [../../skills/natural-japanese]` を宣言している。
`~/.claude` にはプラグイン manifest が無いため、これが無いと両アームが同一構成になり Δ が無意味になる。

## 測定の限界（結果を読む前に必ず読むこと）

**1. lint 工程は検証していない。**
`allowed_tools` から `Bash` を外している。このマシンの `~/.docker` に Docker Desktop 由来の
symlink があり、Bash サンドボックスが起動を拒否するため。結果として
`scripts/lint.py` は実行されず、スキルは `references/manual-checklist.md` の
手動フォールバックで動いている。SKILL.md は lint 省略を明確に禁じている
（「これを飛ばした時点でクイックの品質保証は成立しない」）ので、
**この suite が測っているのは本来の natural-japanese より弱い状態である**。
Docker Desktop の無い環境なら `--allow-tools Write Edit Bash` で本来の工程を測れる。

**2. 素の Claude がすでに強い。**
5回のパイロットを通じ、スキル無しの Opus も短く素性の良い業務文では
読める品質を出した。特に `05`（事実保存）は with/without とも常に満点で、
**最優先の失敗モードである固有名詞・数値の取り違えは、スキルの有無で差がつかない**。
Δ が小さいことはスキルが無価値であることを意味しない。天井に当たっているだけである。

**3. llm グレーダーにはラン間のばらつきがある。**
境界上の出力に対し judge の投票がぶれる。`runs: 3` はその平均化が目的であり、
単発の Δ を根拠に判断してはいけない。

**4. `06` は実環境より厳しい条件である。**
eval サンドボックスには競合する `call-summary` skill が存在しない。
実運用では議事録は call-summary が処理している。この結果が示すのは
「競合が居ない状態で natural-japanese が議事録を掴みにいくか」であって、
実環境での誤発火率ではない。

## 確定した所見（2026-09-17、runs:3 の本番実行 / $11.94 / 42ラン）

| case | with | without | Δ | 読み方 |
|---|---|---|---|---|
| `01-slide-copy` | 1.00 (pass 100%) | 0.60 (pass **0%**) | **+0.40** | **唯一の明確な uplift。** AIスロップが重なった原文では、スキル有無で合格率が 100% 対 0% に割れる |
| `02-memo-from-bullets` | 1.00 (100%) | 1.00 (100%) | 0.00 | 箇条書きからの新規執筆は素の Claude も満点 |
| `03-mail-rewrite` | 0.78 (33%) | 0.78 (33%) | 0.00 | 長文分解の機械判定は両アーム全通過。`readable-mail` ルーブリックが両アームで 1/3 しか通らず、判定が厳しすぎる可能性がある |
| `04-report-conclusion-first` | 0.87 (67%) | 0.93 (67%) | −0.07 | 実質ゼロ。結論先頭化は素の Claude もできる |
| `05-facts-dense` | 1.00 (100%) | 1.00 (100%) | 0.00 | **天井。**2社の数値を指示語で入れ違いに参照する原文でも、両アームとも取り違えゼロ |
| `06-neg-minutes` | 0.50 (0%) | 1.00 (100%) | **−0.50** | 議事録での過剰発火。**2026-09-20 に description を修正して解消済み**（現在は 3/3 で非発火）。経緯は `finding-narrow-description.md` |
| `07-neg-md-to-html` | 1.00 (100%) | 1.00 (100%) | 0.00 | 正しく非発火 3/3 |

平均 Δ −0.02。

### この数字から言えること

**1. uplift は「原文が壊れているとき」にだけ出る。**
`01` は合格率 100% 対 0% という決定的な差がついた。一方 `02` `04` `05` は
素の Claude も満点で、差が出ない。スキルの価値は AI 的な冗長さの除去に集中しており、
構成の組み替えや事実の保存は Claude 単体の能力で足りている。

**2. 最悪の失敗モード（固有名詞・数値の取り違え）は、そもそも起きにくい。**
`05` は指示語で2社の数値を絡ませた意地の悪い入力だが、with/without とも 3/3 で完全保存。
これは「スキルが効いていない」ではなく「心配していた壊れ方が実際には起きない」という所見。

**3. 議事録での過剰発火は本物。**
`06` は 3/3 で発火。SKILL.md の description が議事録を明示的に守備範囲としている以上
仕様どおりだが、実運用では call-summary が処理している。description を狭めるかどうかの判断材料。
ただし「測定の限界 4」のとおり、eval には競合 skill が居ないぶん実環境より厳しい。

**4. `03` のルーブリックは要再検討。**
`readable-mail` が両アームで 1/3 しか通らない。出力品質ではなく判定基準が厳しすぎる疑いがある。
次に触るならここ。

## ケース入力について

実トラフィックの発火ケースは社内の戦略・人事文脈を含み、逐語引用できない。
入力は実ログの「形」（ファイル渡しのリライト、箇条書きからの新規執筆）だけを
保存し、中身は中立な業務文に差し替えた合成である。
