# オーケストレーション方針

メインループ（オーケストレーター）はユーザー指示の解釈、実行方針、統合、完遂に責任を持つ。独立して進められ、委譲の便益がある実作業はサブスレッドに委譲する。

- 委譲する場合は `Agent` ツールで**名前付きサブエージェント**（`fork` ではなく毎回フレッシュな一般サブエージェント）に振る。生のツール呼び出しログをメインループのコンテキストに持ち込まない。フォローアップが要る場合は `SendMessage` で同じ名前のエージェントに再開させる。
- **固定ワーカー役（`.claude/agents/*.md`）は最初からは作らない**（早すぎる抽象化を避ける）。タスクごとに適した既存 skill を探す／その場でプロンプトを書いて委譲する、を都度judgeする。固定役割が明確に繰り返し必要になった時点で改めてsubagents化をユーザーに提案する。
- ユーザーへの確認は、対象と目的に照らして未承認であり、結果を左右する選好、不可逆な操作、課金や外部公開など、本人の判断が必要な選択に限る。公開や課金を含め、現在の依頼ですでに承認された操作は同じ許可を聞き直さない。
- **完遂境界**: 承認済みスコープ内では、必要な実装、検証、発見した自分の変更由来の不具合修正まで進めて完了させる。read-only、レビューのみ、staged-only などの境界が指定されている場合は、その範囲を越えて変更しない。
- **大規模 fan-out は事前承認制**: 4体以上の並列 subagent 起動、`Workflow`(dynamic workflows)、ultracode 等「多数の subagent を一斉に生む」機能を使う前に、規模・目的・トークンコストの概算とトレードオフを説明し `AskUserQuestion` で明示承認を得る。1〜3体の通常委譲は承認不要。
- **独立した作業は並列で**: 互いに依存しない委譲は同一メッセージで複数 `Agent` を起動して並列実行する(逐次にしない)。
- **迷ったら advisor**: 判断に迷う・実装前に一段強いレビューが欲しい・行き詰まった時は `advisor` agent に方針を返させる(実装はさせない)。
- **完了時の独立検証**: 変更が受入基準を満たすかの判断に独立性が有効な場合は、実装を担当していない verifier に合否を判定させる。小さく低リスクな変更では、オーケストレーター自身の確認で十分と判断してよい。
- **herdr環境(`HERDR_ENV=1`)でcodexや別Claude Codeセッションをタスクのデリゲート先として起動する場合、新規tabは作らず現在のtab内にpaneをsplitする**(`herdr pane split --pane <current> --direction right/down`)。新規tab乱立は画面が散らばりユーザーが混乱する(ユーザー本人の明示的指摘)。同一tab内に既存のdelegate用paneが残っていればそれを再利用し(`herdr pane run <pane> "<次のprompt>"`)、新規splitは最後の手段にする。herdr-editのeditor pane方式(同一tab内split・既存pane再利用)と同じ思想で、codex固有のルールではなくherdr環境での委譲全般に適用する。

Orchestrator/Workerのモデル選択方針(既定Fable、委譲時の既定Sonnet、Opus格上げの例外judge等)は `~/.claude/docs/performance.md` の Model Selection Strategy を参照。
