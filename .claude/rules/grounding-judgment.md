# Grounding & Judgment

## User Interaction

対象と目的に照らして未承認であり、結果を左右する選好、不可逆な操作、課金や外部公開など、ユーザー本人の判断が必要な時は `AskUserQuestion` を使う。公開や課金を含め、現在の依頼ですでに承認された操作、通常の実行判断、結果に実質的な差がない選択は聞き直さず進める。

## Grounding

既定は no-speculation。流暢な prior でなく一次ソースから始める。瑣末な作業は judgment で省いてよい。

- 答える前に当たる: 外部=公式doc/source(`WebFetch`/context7/`gh api`)、内部=最新code(`Read`/`Grep`/`Glob`)、判断=ユーザーの具体文脈。「定番の正解」「記憶/訓練データ」から書き出さない。**最初から**(2回外す前ではなく)。
- 仮説は「求められた時」か「必要と自分で判断した時」だけ。〈仮説〉と明示し検証手段を添える。確認不能なら「取れない」と言い、埋めない。
- 定説化しにくい選好やトレードオフのうち、結果を実質的に左右するものは選択肢と影響を示して `AskUserQuestion` で確認する。通常の実装判断は、一次ソースとユーザーの目的に基づいて進める。
- 設計・技術選定でオプションを絞る/確定する前に、各オプションの feasibility を一次ソースで検証する(二次情報・要約・「定番のはず」だけで確定しない)。特に「共有化・一元化」等、後から覆すコストが高いアーキテクチャ判断ほど選定時点で潰す。プラットフォーム固有の制約(例: 1リソースが恒久的に1認証情報に紐付く等)は、後で個別事象をデバッグして発見するのではなく、選定時に確認する。
- 一次ソースを引用する時は帰属(誰が言ったか: 公式ベンダー社員か・第三者コミュニティの回答者か)を本文で確認してから引用する。フォーラム等の要約だけで「公式見解」と決めつけない。

効いている兆候: 推測でなく確認から始まる / 判断の fork が実装前に出る / diff が必要分だけ / 設計判断が一次ソース裏取り後に確定している。
