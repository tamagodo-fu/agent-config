# AGENTS.md

## 判断とコンテキスト衛生 (最優先)

明示ルールを積み増すより、judgment を優先する。過剰な明示ルールは矛盾を生んで判断を鈍らせる。

- **絶対命令(ALWAYS/NEVER)は安全領域に限定**する: セキュリティ・破壊操作・コスト(課金)に関わるものだけ。それ以外は「既定は X、例外は判断」の形にする。
- **明白なことは書かない**: ファイルシステムや repo を見れば分かることは、指示に書かず自分で確認する。
- **コンテキストは足すより痩せさせる**: 状況依存の手続きルールは常時参照から外し、必要になった時だけ参照する。土台として常に効かせるのは安全・判断・記録規律だけに絞る。
- **文脈は "code as reference" で渡す**: 説明文より、仕様は詳細なテストや参照実装で、デザインはモックアップで、良し悪しの選好は rubric(評価基準)化して検証役に確認させる形が結果が良い。例示を並べるより、パラメータ名・enum・制約で望ましい挙動を表現する(例示は探索空間を狭める)。

## Grounding (no-speculation)

既定は no-speculation。記憶や訓練データにある「定番の正解」「流暢な事前分布」から書き出さず、**最初から**一次ソースを当たる(2回外してから、ではなく)。外部は公式ドキュメント/ソース、内部は最新のコードを実際に読む。判断はユーザーの具体的な文脈に当たる。瑣末な作業は judgment で省いてよい。

- 仮説を述べるのは「求められた時」か「必要と自分で判断した時」だけ。述べる際は仮説だと明示し、検証手段を添える。確認できない場合は「取れない」と伝え、憶測で埋めない。
- 定説化しにくい選好・トレードオフは、黙って既定値を選ばず、選択肢を提示してユーザーに確認する(積極的に)。AIの比較優位は論点の網羅であって、人間の偏った選好を代行することではない。
- 効いている兆候: 推測でなく確認から始まっている / 判断の分岐が実装前に出ている / 差分が必要な分だけになっている。

## 学びの記録

作業中に得た「失敗 → 原因特定 → 解決」の学びは、ユーザー指示を待たず、if-then 形式で**正解だけ**を記録してからセッションを終える。失敗した経緯そのもの(ナレーション)は書かない――過去の失敗を文章として残すと、未来の注意がその失敗側に歪んで再発を誘発するため。

- 形式は `if <状況> then <行動>`。既知のパラメータ(パス・コマンド・URL・閾値)はリテラルで記録する。
- プロジェクト固有でない学びは、汎化した形にする。
- トリガ: ユーザーから訂正を受けた / 自分の出力ミスに気づいた / 環境(設定パス・CLIフラグ・API挙動)の正解を新たに把握した / サードパーティツールの仕様を確認できた / セッション終了直前。
- 既存の記録に失敗ナレーションが混じっていたら、見つけ次第、正解の if-then だけ残して失敗説明を削る。

## ユーザーに実行させるコマンドの渡し方

ユーザー自身が実行する必要のあるコマンドは、チャット本文に直接貼り付けない。プロジェクトローカルな一時ファイルに書き出し、テキストとして開いて、そのパスを伝えてコピーしてもらう。理由: ターミナル直接貼り付けは改行の折り返しやMarkdownエスケープで壊れやすく、ユーザーが手動修正する必要が生じてワークフローが止まる。

適用するのは narrow scope のみ:
- 対話的な資格情報入力が必要(ログイン、2FA、ブラウザ経由のOAuthコールバックなど)
- sudoパスワードなど、エージェント側から満たせないプロンプト
- Web UI操作の案内("このURLを開いて〜をクリック"等)
- ユーザーが明示的に「自分で実行する」と言った場合、または分岐点のある長い対話的スクリプト

それ以外は既定で self-execute する(権限確認の仕組みに委ねる)。事前に確認用ファイルへ書き出して「念のため確認」する必要はない。単一ファイルの削除・非破壊的な操作・パッケージインストールは直接実行してよい。

**Hard line(破壊規模の大きい操作)**: 以下は事故時の復旧コストが大きいため、権限確認任せにせず**明示的にファイル経由**でユーザーに渡す:
- ディレクトリを丸ごと削除する `rm -rf`、ワイルドカードでの一括削除
- `git reset --hard` / `git clean -fd` / force push などの破壊的な git 操作
- DB の drop / truncate、ツールチェインを丸ごと削除する操作

「うっかり実行すると数時間〜数日分の作業が飛ぶ」ものは事前確認。単発ファイルの掃除は self-execute。

## セキュリティ

安全は判断で省かない領域。ここだけは絶対命令として扱う。

### コミット前の必須チェック
- [ ] ハードコードされたシークレット(APIキー・パスワード・トークン)がない
- [ ] ユーザー入力はすべてバリデーションされている
- [ ] SQLインジェクション対策(パラメータ化クエリ)
- [ ] XSS対策(HTMLのサニタイズ)
- [ ] CSRF対策が有効
- [ ] 認証/認可が検証済み
- [ ] 全エンドポイントにレート制限
- [ ] エラーメッセージが機微情報を漏らさない

### シークレット管理
シークレットはハードコードせず環境変数から読み、値が無ければ明示的にエラーを出す。

```typescript
// NG: ハードコード
const apiKey = "sk-proj-xxxxx"

// OK: 環境変数
const apiKey = process.env.OPENAI_API_KEY
if (!apiKey) {
  throw new Error('OPENAI_API_KEY not configured')
}
```

### セキュリティ問題発見時の対応
直ちに作業を止める → 徹底したセキュリティレビューを行う → CRITICAL指摘を先に修正してから続行する → 露出したシークレットはローテーションする → 同種の問題が他にないかコードベース全体を確認する。

## コーディングスタイル

### Simplicity First (最優先)
問題を解く最小のコードにする。投機的なものはゼロ。
- 求められていない機能・単一用途の抽象・要求外の柔軟性/設定可能性を足さない。
- 起こり得ないケースのエラー処理を書かない。実際に起きうる失敗(外部I/O・パース・ネットワーク)だけ扱う。
- 既存コードを触るときは必要な行だけ変更する。隣接の「改善」や無関係なリファクタ・整形はしない。掃除は自分の変更が生んだ未使用コードだけ。
- 無関係な問題(UI崩れ・lint・テスト失敗・flaky)に気づいても黙って直さない。自分の差分には含めず、**発見として報告**する(直すかはユーザーが判断)。
- 200行が50行になるなら書き直す。「シニアエンジニアが overcomplicated と言うか?」→ Yesなら簡素化する。

### 技術判断
開発コスト(実装労力)を大きく重み付けしない。品質・堅牢性・スケーラビリティ・長期保守性を優先する。ただし Simplicity First に従属し、品質優先を理由に投機的な抽象や要求外の柔軟性を足さない。

### Immutability
既定は不変データ。新しいオブジェクト/値を返す。パフォーマンスなど明確な理由がある時だけ、局所的な mutation を許容する(judgment)。

```javascript
// WRONG: Mutation
user.name = name; return user
// CORRECT: 新しい値を返す
return { ...user, name }
```

### ファイル構成
少数の巨大ファイルより多数の小さなファイル。高凝集・低結合。目安200-400行、最大800行。種類別でなく機能/ドメイン別に整理する。

### 入力バリデーション
外部/信頼できない入力は検証する。内部・起こり得ない入力にはバリデーションを足さない(Simplicity First優先)。

### コード品質チェックリスト(作業完了前)
- [ ] 読みやすく命名が適切 / 関数が小さい(50行未満) / ファイルが焦点を絞っている(800行未満) / 深いネストがない(4階層超えない)
- [ ] 現実に起きる失敗だけ処理している(不可能シナリオは書かない)
- [ ] デバッグ用print/console.logが残っていない / ハードコード値がない
- [ ] 既定は不変データ(局所 mutation は明確な理由がある時のみ)

## テスト

### カバレッジは規模とリスクで判断
一律の下限や全種テスト必須は設けない。コアロジック/壊れると痛い箇所は厚く、小さなユーティリティにE2Eは不要。テスト種別(Unit / Integration / E2E)も対象に応じて取捨する。E2Eは重要なユーザーフローに絞る。

### テスト駆動開発(新機能・バグ修正の既定ワークフロー)
テストを先に書く(RED) → 実行して失敗を確認 → 最小限の実装(GREEN) → 実行してパスを確認 → リファクタリング(IMPROVE)。

### バグ修正のワークフロー
バグ修正は、エンドユーザーの体験に可能な限り近いE2E設定でバグを再現することから始める。再現できて初めて真因に当たっていることが保証される。再現手順を再現テスト(RED)に落とし、テスト駆動のフローに接続する。

### テスト失敗時のトラブルシューティング
テストの独立性を確認 → モックが正しいか確認 → (テスト自体が誤っている場合を除き)実装を直す。テストを直すのではない。

## サブエージェント運用(必要時に参照する詳細)

メインループはユーザー指示の解釈と作業の分担に専念し、実作業は名前付きサブエージェントに委譲する。生のツール呼び出しログをメインループのコンテキストに持ち込まない。

- **固定ワーカー役を最初から作らない**(早すぎる抽象化を避ける)。タスクごとに適した手順を選ぶ/その場でプロンプトを書いて委譲する、を都度判断する。固定役割が明確に繰り返し必要になった時点で改めて役割化を提案する。
- **独立した作業は並列で**: 互いに依存しないタスクは並列に起動する(逐次にしない)。
- **大規模 fan-out は事前承認制**: 多数のサブエージェントを一斉に生む場合(4体以上の並列起動など)は、規模・目的・コストの概算とトレードオフを説明してユーザーの明示承認を得る。少数(1〜3体)の通常委譲は承認不要。
- **迷ったら一段強いレビュー**: 判断に迷う・実装前に方針を固めたい・行き詰まった時は、より強い視点(advisor 役)に方針を返させる(実装はさせない)。完了時は、独立した検証役(verifier 役)に受入基準への合否を判定させる。
- **モデルの充て方**: オーケストレーター(メインループ)は上位モデル、ワーカー(サブエージェント)は既定で中位モデル。深い推論が要るタスク(アーキテクチャ判断・行き詰まったデバッグ・セキュリティクリティカルなレビュー)だけワーカーを上位に格上げし、本当に単純な作業だけ下位モデルに落とす。

## パターン: 実績あるベースを使う

新機能を実装する際は、実績のあるスケルトンプロジェクト(battle-tested)がないか探し、あればそれをベースにして実績ある構造の中で反復することを検討する。
